## ВВЕДЕНИЕ

Сегодня большинство людей ищут работу через интернет. На сайтах вроде hh.ru, Superjob или «Работа России» можно посмотреть тысячи вакансий, откликнуться на понравившиеся и следить за откликами. Для студента по специальности «Информационные системы и программирование» полезно не только пользоваться такими сервисами, но и понимать, как они устроены изнутри.

Актуальность темы связана с тем, что рынок труда всё больше переходит в онлайн. Работодателям и соискателям нужны удобные программы: с поиском, личным кабинетом и возможностью сохранять интересные объявления. Создание собственного веб-приложения — хороший способ показать на защите диплома, что выпускник умеет проектировать базу данных, писать сервер и делать понятный интерфейс.

Объектом исследования является процесс поиска и хранения информации о вакансиях в веб-приложении.

Предметом исследования выступают программные средства для построения сайта ChifBoard: регистрация пользователей, поиск вакансий, личный кабинет.

Целью работы является разработка веб-приложения ChifBoard, в котором можно искать вакансии, добавлять их в личный кабинет и работать с российским каталогом объявлений.

Для достижения поставленной цели необходимо решить следующие задачи:

- разобраться в предметной области и существующих аналогах;
- сформулировать требования к системе;
- спроектировать базу данных и архитектуру;
- реализовать интерфейс и серверную логику;
- развернуть приложение и проверить его работу.

В ходе выполнения работы использовались следующие методы исследования: анализ и обобщение информации, проектирование программного обеспечения, разработка и тестирование веб-приложения.

Практическая значимость состоит в том, что в результате получается готовый сайт, который можно показать на защите, запустить на своём компьютере и при необходимости доработать, например подключить реальный API hh.ru.

## 1. АНАЛИЗ ПРЕДМЕТНОЙ ОБЛАСТИ. ПОСТАНОВКА ЗАДАЧИ

### 1.1. Описание предметной области

В современном мире поиск работы всё чаще начинается с интернета. Соискатель заходит на сайт или в приложение, вводит должность, город или ключевое слово, просматривает список предложений и сохраняет те, которые кажутся подходящими. Работодатель, в свою очередь, публикует объявление с названием должности, названием компании, зарплатой, требованиями и условиями работы.

Такие сервисы относятся к классу информационных систем в сфере занятости. Их задача — помочь быстро найти нужную информацию среди большого числа объявлений и организовать работу с ней: просмотреть, сравнить, сохранить на потом.

Раньше вакансии искали в газетах и на досках объявлений. Сейчас основной канал — веб-сайты и мобильные приложения. У них есть общие черты: каталог вакансий, поиск по словам, иногда — личный кабинет, куда пользователь складывает понравившиеся предложения. Крупные площадки вроде hh.ru добавляют резюме, отклики, платные услуги для работодателей. Для учебного проекта достаточно базового набора: поиск, просмотр, сохранение в кабинет, регистрация.

В разрабатываемом приложении ChifBoard реализованы следующие возможности:

- просмотр и поиск вакансий в локальной базе данных;
- отдельный каталог российских вакансий (69 объявлений с зарплатами в рублях, городами РФ, датами публикации до 19.06.2026);
- публикация новой вакансии через форму на сайте;
- регистрация и вход пользователя по логину и паролю;
- личный кабинет с сохранёнными вакансиями;
- добавление вакансии в кабинет кнопкой «+».

Важная особенность: добавить вакансию в личный кабинет может только авторизованный пользователь. Если человек не вошёл в аккаунт и нажимает «+», система не выполняет добавление, а перенаправляет его на страницу входа. Это защищает личные данные и не даёт сохранять вакансии «в никуда».

Основными функциями ChifBoard являются:

- поиск вакансий по названию, компании, городу и описанию;
- просмотр российского каталога через отдельную кнопку;
- добавление своей вакансии в общий список;
- регистрация и авторизация;
- сохранение понравившихся вакансий в личный кабинет;
- просмотр и удаление сохранённых записей;
- запрет повторного добавления одной и той же вакансии.

Использование подобных систем актуально для соискателей любого возраста и профессии. Студент может искать подработку или стажировку, специалист — постоянную работу. Удобный интерфейс, понятные поля (должность, зарплата, город) и возможность вернуться к сохранённым объявлениям делают процесс поиска менее хаотичным.

Одной из тенденций на рынке является адаптация контента под конкретную страну: зарплаты в рублях, города России, упоминание оформления по ТК РФ, ДМС, графика 5/2 или удалённой работы. Каталог в ChifBoard составлен с учётом этих особенностей, чтобы вакансии выглядели реалистично для российского соискателя.

Таким образом, анализ предметной области показывает, что веб-приложения для поиска работы востребованы и решают понятную практическую задачу. Ключевые требования к таким системам — удобный поиск, личный кабинет, защита данных пользователя и понятный интерфейс на русском языке.

### 1.2. Классификация приложений для поиска работы

Приложения и сайты для поиска работы можно разделить на несколько групп в зависимости от масштаба, аудитории и способа хранения данных.

Первую группу составляют крупные агрегаторы: hh.ru, Superjob, «Работа России», Zarplata.ru. У них миллионы вакансий, мобильные приложения, резюме, отклики, иногда — платные услуги. Плюс — огромная база и узнаваемость. Минус для учебного проекта — закрытый код, сложная инфраструктура, частично платный API.

Вторую группу образуют корпоративные карьерные порталы. Это раздел «Вакансии» на сайте одной компании или холдинга. Пользователь видит только предложения этой организации. Такой формат удобен работодателю, но не подходит как универсальный инструмент для соискателя.

Третью группу можно назвать учебными и демонстрационными приложениями. Их делают студенты или начинающие разработчики для диплома, курсовой или портфолио. Код открыт, архитектура проще, функционал базовый: поиск, список, иногда регистрация и личный кабинет. Именно к этой группе относится ChifBoard.

По способу хранения данных различают:

- полностью серверные системы (данные в базе на сервере, клиент только показывает интерфейс);
- клиентские приложения с локальным хранением (данные только в браузере);
- смешанные решения (каталог на сервере, личные данные пользователя — в базе после входа).

ChifBoard относится к серверному типу: PostgreSQL хранит пользователей, опубликованные вакансии и записи личного кабинета. Каталог российских вакансий лежит в отдельном файле на сервере и отдаётся через API без обращения к внешним сайтам.

По функционалу для соискателя можно выделить:

- только просмотр и поиск (гостевой режим);
- просмотр плюс личный кабинет (нужна регистрация);
- полный цикл с резюме и откликами (в ChifBoard не реализован — это возможное развитие).

Анализ показывает, что для дипломного проекта оптимален вариант с сервером, базой данных, регистрацией и личным кабинетом. Это позволяет показать полный цикл разработки и типичные задачи backend- и frontend-разработчика.

### 1.3. Выбор средств и технологий разработки

При разработке веб-приложения ChifBoard был выбран стек технологий, который часто используют для небольших и средних проектов и который хорошо подходит для учебной работы.

В качестве серверной платформы выбран Node.js. Это среда выполнения JavaScript вне браузера. Один язык используется и на клиенте, и на сервере, что упрощает разработку и сопровождение небольшого проекта.

Для организации HTTP-сервера и маршрутов API применяется фреймворк Express. Он позволяет задавать адреса вроде `/api/jobs` или `/api/auth/login`, подключать промежуточные обработчики (middleware) для проверки авторизации и возвращать ответы в формате JSON.

Данные хранятся в PostgreSQL — реляционной системе управления базами данных. В ней удобно описывать таблицы пользователей и вакансий, связывать записи личного кабинета с конкретным пользователем, задавать уникальные индексы для защиты от дубликатов.

Клиентская часть построена на HTML, CSS и JavaScript без дополнительных фреймворков (Vanilla JS). Страница переключает разделы — «Просмотр вакансий», «Личный кабинет», «Вход» — без полной перезагрузки. Запросы к серверу выполняются через Fetch API.

Настройки подключения к базе (логин, пароль, адрес) вынесены в файл `.env`, который не попадает в репозиторий. Для работы с переменными окружения используется пакет dotenv.

Каталог из 69 российских вакансий оформлен отдельным модулем `russian_jobs.js`. Так проще обновлять демонстрационные данные без правки основного кода сервера.

Альтернативы вроде PHP + MySQL или Python + Django тоже подошли бы, но Node.js и Express широко описаны в документации, часто встречаются в вакансиях для начинающих разработчиков и позволяют быстро поднять REST API.

Таким образом, выбранный стек обеспечивает баланс между простотой и наглядностью: есть и сервер, и база данных, и работающий интерфейс, и всё это можно запустить локально на одном компьютере.

## 2. ПРОЕКТИРОВАНИЕ ВЕБ-ПРИЛОЖЕНИЯ

### 2.1. Постановка задачи

На основании анализа предметной области сформулирована задача дипломной работы — разработать веб-приложение ChifBoard для поиска и управления вакансиями с регистрацией пользователей и личным кабинетом.

Разрабатываемое приложение должно работать в браузере и обращаться к серверу на Node.js. Данные пользователей и сохранённые вакансии хранятся в PostgreSQL. Отдельно предусмотрен каталог российских объявлений для демонстрации поиска по рынку труда РФ.

Ключевые задачи, которые нужно решить в ходе разработки:

- спроектировать структуру базы данных для пользователей, общих вакансий и личного кабинета;
- реализовать регистрацию, вход и выход с проверкой данных;
- сделать поиск по локальной базе и по российскому каталогу;
- добавить кнопку «+» для сохранения вакансии в личный кабинет;
- запретить добавление без авторизации и перенаправлять на страницу входа;
- не допускать повторного добавления одной и той же вакансии;
- обеспечить просмотр и удаление записей в личном кабинете;
- подготовить инструкцию по локальному запуску.

Особенностью решения является разделение общего каталога вакансий и персонального списка каждого пользователя. Гость может только смотреть и искать. Авторизованный пользователь дополнительно управляет своим кабинетом.

Сформулированная задача определяет дальнейшую работу и служит основой для требований к системе, рассмотренных в следующем подразделе.

### 2.2. Требования к системе

При проектировании ChifBoard были определены функциональные и нефункциональные требования.

Функциональные требования описывают, что система должна уметь делать для пользователя.

В рамках приложения необходимо обеспечить следующий функционал:

- поиск вакансий в локальной базе по ключевым словам;
- просмотр российского каталога (69 вакансий) через отдельную кнопку;
- добавление новой вакансии через форму (название, компания, город, зарплата, описание);
- регистрация пользователя с проверкой уникальности логина;
- вход и выход из аккаунта;
- добавление вакансии в личный кабинет кнопкой «+»;
- блокировка добавления для неавторизованных пользователей с автоматическим переходом на страницу входа;
- запрет повторного сохранения одной и той же вакансии;
- просмотр полной информации о сохранённой вакансии;
- удаление вакансии из личного кабинета;
- навигация между разделами «Просмотр вакансий» и «Личный кабинет» без выхода из аккаунта.

Типичный сценарий работы выглядит так. Пользователь открывает сайт, ищет вакансии по слову «аналитик» или нажимает «Российские вакансии». Находит подходящее объявление и нажимает «+». Если он не вошёл — открывается форма входа. После входа вакансия сохраняется, кнопка меняется на «✓». В личном кабинете пользователь видит все сохранённые записи, может открыть любую или удалить.

Нефункциональные требования:

- пароли хранятся в виде хеша, а не открытым текстом;
- доступ к API личного кабинета только с действительным токеном;
- интерфейс на русском языке;
- возможность запуска на Windows при установленных Node.js и PostgreSQL;
- понятная структура файлов проекта для демонстрации на защите.

Таким образом, сформулированные требования задают границы проекта и используются при проектировании архитектуры и реализации.

### 2.3. Проектирование архитектуры приложения

Проектирование архитектуры — важный этап, от которого зависит, как части системы будут связаны между собой и как их потом дорабатывать.

ChifBoard построен по схеме «клиент — сервер — база данных». Это классический трёхуровневый подход для веб-приложений.

На уровне представления работает браузер пользователя. Он загружает HTML-страницу, стили CSS и скрипт app.js. Интерфейс переключает видимые блоки без перезагрузки всей страницы.

На уровне бизнес-логики работает сервер Express в файле server_clean.js. Он принимает HTTP-запросы, проверяет авторизацию, выполняет SQL-запросы к PostgreSQL и возвращает JSON.

На уровне данных — PostgreSQL с таблицами jobs, users и saved_jobs.

Структура проекта:

- server_clean.js — главный файл сервера;
- db.js — подключение к базе;
- db.sql — описание таблиц;
- russian_jobs.js — каталог российских вакансий;
- public/index.html — разметка;
- public/app.js — логика в браузере;
- public/styles.css — оформление.

Таблица users хранит зарегистрированных пользователей: id, username (уникальный логин), password_hash, дата регистрации.

Таблица jobs — вакансии, которые добавляют через форму на сайте: название, компания, город, зарплата, описание, дата.

Таблица saved_jobs — вакансии в личном кабинете конкретного пользователя. Поле user_id связывает запись с таблицей users. Поля source и external_id нужны, чтобы не добавлять одну вакансию дважды.

При удалении пользователя его записи в saved_jobs удаляются автоматически (ON DELETE CASCADE).

Основные маршруты API:

- POST /api/auth/register — регистрация;
- POST /api/auth/login — вход;
- POST /api/auth/logout — выход;
- GET /api/jobs — поиск в локальной базе;
- GET /api/russian-jobs — российский каталог;
- GET/POST/DELETE /api/my-jobs — личный кабинет (требуется токен).

## 3. РЕАЛИЗАЦИЯ ВЕБ-ПРИЛОЖЕНИЯ

### 3.1. Разработка интерфейса приложения

Интерфейс — та часть приложения, с которой пользователь работает напрямую. При разработке ChifBoard основной задачей было сделать понятную навигацию и быстрый доступ к поиску, входу и личному кабинету.

Приложение реализовано как одностраничный интерфейс: все основные разделы находятся в одном HTML-файле, переключение выполняется через JavaScript без полной перезагрузки страницы.

В шапке сайта расположены кнопки навигации: «Просмотр вакансий», «Личный кабинет», «Вход» (или имя пользователя и «Выйти», если человек уже авторизован). Это позволяет в любой момент вернуться к списку вакансий, не выходя из аккаунта.

### 3.2. Реализация логики приложения

Логика приложения разделена между сервером и браузером.

На сервере при запуске вызывается функция ensureTables(). Она создаёт таблицы jobs, users и saved_jobs, если их ещё нет в базе.

При регистрации проверяется длина логина (не менее 3 символов) и пароля (не менее 4). Система ищет в базе пользователя с таким же логином. Если он уже есть — возвращается ошибка. Пароль хешируется через crypto.scrypt и сохраняется в поле password_hash. Пользователю выдаётся токен сессии.

При входе логин и пароль сверяются с данными в базе. При успехе также выдаётся токен.

Маршруты личного кабинета защищены middleware authMiddleware. Без заголовка Authorization: Bearer … запрос отклоняется с кодом 401.

При добавлении вакансии в кабинет (POST /api/my-jobs) сервер проверяет, нет ли уже такой записи у этого пользователя. Если есть — ответ 409 с текстом «Эта вакансия уже добавлена в личный кабинет».

Каталог российских вакансий отдаётся маршрутом GET /api/russian-jobs. Данные берутся из файла russian_jobs.js, при необходимости фильтруются по параметру q и сортируются по дате (сначала новые).

На клиенте токен сохраняется в localStorage. При загрузке страницы выполняется запрос GET /api/auth/me — если токен действителен, пользователь считается авторизованным.

Для защиты кнопки «+» используется функция requireAuthForAdd(). Если пользователь не вошёл, вызывается redirectToLogin(): открывается вкладка «Вход», показывается сообщение «Для добавления вакансии необходимо войти в аккаунт», запрос на сервер не отправляется.

Фрагмент кода:

```javascript
function requireAuthForAdd() {
  if (currentUser && getToken()) return true;
  redirectToLogin('Для добавления вакансии необходимо войти в аккаунт');
  return false;
}
```

При клике на «+» сначала вызывается эта проверка. Только после успешного входа выполняется saveJobToCabinet().

Если сессия истекла и сервер вернул 401, токен сбрасывается, пользователя снова перенаправляет на страницу входа.

После успешного добавления кнопка «+» меняется на «✓». Повторное нажатие на ту же вакансию не создаёт дубликат — ни на клиенте, ни на сервере.

### 3.3. Разворачивание приложения

После разработки приложение нужно запустить на компьютере, чтобы проверить его работу и показать на защите.

Для ChifBoard используется локальное развёртывание: сервер Node.js и база PostgreSQL на том же компьютере, где идёт разработка.

Первый шаг — установить Node.js и PostgreSQL.

Второй шаг — создать базу данных, например job_board:

```sql
CREATE DATABASE job_board;
```

Третий шаг — создать в корне проекта файл .env:

```
DATABASE_URL=postgres://user:password@localhost:5432/job_board
PORT=3000
```

Вместо user и password подставляются реальные данные для подключения к PostgreSQL.

Четвёртый шаг — в папке проекта выполнить команды:

```
npm install
npm start
```

При успешном запуске в консоли появляются строки:

```
DB check: tables are ready
Server running on http://localhost:3000
```

Пятый шаг — открыть в браузере адрес http://localhost:3000.

Таблицы в базе создаются автоматически при первом запуске. Отдельно выполнять db.sql не обязательно, но файл можно использовать для проверки структуры.

Остановить сервер можно сочетанием Ctrl+C в терминале. Если порт 3000 занят, в .env меняют PORT или завершают старый процесс.

После изменения server_clean.js или russian_jobs.js сервер нужно перезапустить, иначе браузер будет работать со старой версией кода.

Таким образом, развёртывание сводится к установке ПО, настройке .env и запуску npm start. Этого достаточно для демонстрации всех функций приложения на защите диплома.

```javascript
function authMiddleware(req, res, next) {
  const token = req.headers.authorization?.slice(7);
  if (!token || !sessions.has(token)) {
    return res.status(401).json({ error: 'Требуется авторизация' });
  }
  req.userId = sessions.get(token);
  next();
}
```
